# Package audit improvements

Approved scope: compatible development-tool security updates, automated audit checks,
and fresh packaging, type and bundle measurements. No runtime API changes or release.

## Evidence before changes

- Published candidate: `2.3.0-rc.1`; stable `2.2.0`.
- Bundlephobia: candidate 37,278 minified bytes / 10,240 gzip bytes;
  stable 32,525 / 8,951. Both have zero dependencies, ESM and no side effects.
- publint and Are the Types Wrong pass.
- npm audit: 21 development findings (7 high, 13 moderate, 1 low).
- npm audit --omit=dev: zero findings.
- npms.io: HTTP 404; Socket: HTTP 403. Neither establishes a package defect.

## Implementation plan

- [x] Update vulnerable development dependencies within their existing major versions.
  Inspect remaining advisories and dependency paths before any override; do not use
  `npm audit fix --force` or change supported runtime versions.
- [x] Add a scheduled/read-only security workflow with full and production audits,
  preserving reports even on failure. Keep external service availability out of PR gates.
- [x] Run full tests, lint, typecheck, build, publint, Are the Types Wrong, package
  verification, consumer smoke and existing bundle budgets after dependency changes.
- [x] Record exact results and limitations with links to external services. Preserve
  existing budget thresholds and public package version. Do not claim local changes
  improve measurements of an already published version.

## Acceptance criteria

Zero known production vulnerabilities; eliminate compatible development findings or
document the precise unresolved provider constraint. Existing compatibility and
consumer bundle checks must pass without relaxed limits. No runtime dependency,
source API change, npm publication or dist-tag change.
