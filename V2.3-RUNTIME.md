# Guía de ejecución 2.3

Esta guía resume las APIs de ejecución incorporadas en la línea 2.3, cuándo conviene usarlas y qué garantías ofrecen. Los operadores funcionales se componen con `pipe`; `run` añade identidad, metadatos, observabilidad y cancelación de una invocación.

```ts
import { run } from 'annotations-design-patterns/run';
import { pipe } from 'annotations-design-patterns/pipe';
import { retry, timeout } from 'annotations-design-patterns/operators';

const load = pipe(async (id: string) => fetchRecord(id), timeout(2_000), retry({ attempts: 3 }));

const record = await run({}, ['record-42'], load, {
  operationId: 'load-record-42',
});
```

Los ejemplos usan importaciones por subruta para mostrar dónde vive cada API. `StateMachine` se exporta desde la raíz; `executionMethod` y `run` se importan desde `annotations-design-patterns/run`. Las APIs señaladas como experimentales pueden cambiar en una versión posterior.

## Admisión por ventana: `rateLimit`

`rateLimit` permite hasta `limit` admisiones dentro de una ventana deslizante de `windowMs`. El estado comienza cuando se aplica el operador a un método y se comparte entre las llamadas de ese método. La ventana usa el reloj monótono `performance.now()`.

```ts
import { pipe } from 'annotations-design-patterns/pipe';
import { rateLimit } from 'annotations-design-patterns/operators';

const send = pipe(
  async (recipient: string, message: string) => deliver(recipient, message),
  rateLimit({ limit: 20, windowMs: 60_000 }),
);

await send('ops@example.test', 'ready');
```

Una llamada que supera el límite falla inmediatamente con `RateLimitExceededError`, que extiende `PolicyError`; `retryAfterMs` indica cuánto falta para que vuelva a caber una admisión. `isRateLimitExceededError` reconoce la marca del error entre copias ESM y CJS del paquete. Una cancelación que ya llegó antes de la admisión no consume cuota. Una llamada admitida sí consume cuota aunque el cuerpo lance una excepción o se cancele: el límite cuenta admisiones, no éxitos.

Los valores deben ser un entero seguro positivo para `limit` y un número finito positivo para `windowMs`. El operador limita llamadas locales a ese método; no coordina procesos ni servidores.

## Cachés locales: capacidad y cancelación compartida

### `memoize` y `cachedFor`

`memoize` mantiene resultados por clave. `cachedFor(ttlMs, options)` añade expiración temporal. Ambas APIs aceptan `maxEntries`, un límite positivo de entradas conservadas, incluidos los resultados aún pendientes. La política es FIFO: una entrada nueva puede expulsar a la más antigua; los aciertos no cambian su orden. Esto acota memoria retenida, no el número de operaciones que siguen ejecutándose después de ser expulsadas.

```ts
import { cachedFor, memoize } from 'annotations-design-patterns/operators';

const lookup = memoize<unknown, [string], User>({
  key: (id) => id,
  maxEntries: 500,
});

const getUser = cachedFor<unknown, [string], User>(30_000, {
  key: (id) => id,
  maxEntries: 500,
  perReceiver: true,
});
```

`perReceiver: true` crea un espacio de claves por receptor. Las variantes `memoizeWithHandle` y `cachedForWithHandle` devuelven `{ operator, handle }`; el handle permite invalidar una clave o limpiar las entradas, y ese caché pertenece a esa instancia de fábrica. Las variantes funcionales sin handle conservan estado por método aplicado.

La capacidad se aplica por partición: con `perReceiver`, cada receptor puede conservar hasta `maxEntries`; no es un límite global entre receptores. Sin capacidad explícita el caché sigue sin límite de entradas. La expiración es perezosa.

### Retirada cooperativa del último consumidor

La opción experimental `cancelWhenUnused: true` está disponible para `memoize`, `cachedFor` y `overlap` en modo `share`. Las llamadas que comparten una entrada pendiente se convierten en consumidores de una misma ejecución. Cuando un consumidor retira su propia señal, deja de esperar. Si queda otro consumidor, el trabajo compartido sigue. Cuando se retira el último, la entrada deja de ser visible para nuevas llamadas y el operador aborta la señal que recibió el trabajo compartido.

```ts
import { executionMethod, run } from 'annotations-design-patterns/run';
import { memoize } from 'annotations-design-patterns/operators';
import { pipe } from 'annotations-design-patterns/pipe';

const fetchUser = executionMethod(async ({ signal }, id: string) => {
  const response = await fetch(`/users/${encodeURIComponent(id)}`, { signal });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return (await response.json()) as User;
});

const sharedFetch = pipe(
  fetchUser,
  memoize<unknown, [string], User>({
    key: (id) => id,
    maxEntries: 200,
    cancelWhenUnused: true,
  }),
);

const caller = new AbortController();
const result = run({}, ['u-17'], sharedFetch, { signal: caller.signal });
caller.abort(new Error('La vista dejó de necesitar el usuario'));
```

El trabajo solo puede detenerse físicamente si el método subyacente atiende la `AbortSignal`. Sin señal, un consumidor permanece asociado hasta que termina el trabajo. La expulsión por capacidad, la expiración y la invalidación no cuentan como retirada de un consumidor ni cancelan por sí solas el trabajo. Si el código compartido espera cíclicamente el resultado de otra llamada que depende de esa misma entrada, puede bloquearse; ese patrón no está soportado.

Sin esta opción se conserva el comportamiento anterior, incluida la identidad de promesas sin señal. Al activarla, el operador posee una promesa de reserva y cada consumidor con señal puede recibir su propia espera: no se promete la identidad anterior. Un iniciador síncrono sigue devolviendo su valor síncrono; una llamada reentrante que se une a una reserva recibe una promesa. La ejecución física usa los metadatos del iniciador y una raíz de cancelación propia; no combina los metadatos de todos los consumidores.

Para que la cancelación contextual llegue al método, compónlo con `pipe`/`run`. `operator.apply()` y los envoltorios opacos ordinarios son límites explícitos de contexto; no hay propagación ambiental. `applyWithContext` es infraestructura interna y no forma parte del contrato público `Operator`.

## Métodos con contexto explícito: `executionMethod`

`executionMethod` adapta una función que recibe primero un objeto de ejecución de solo lectura. Incluye el receptor, argumentos congelados, clave, `operationId`, metadatos y la señal efectiva cuando existe. La función adaptada conserva exactamente su tipo de retorno, incluso si es síncrono. Una llamada directa recibe `signal: undefined`; `run` y `pipe` propagan el contexto. Un operador como `timeout` puede crear una señal derivada, por lo que el método debe usar la señal que recibe y no asumir que siempre será idéntica a la del llamador.

```ts
import { executionMethod, run } from 'annotations-design-patterns/run';
import { pipe } from 'annotations-design-patterns/pipe';
import { timeout } from 'annotations-design-patterns/operators';

const search = executionMethod(async ({ signal, operationId }, query: string) => {
  console.log('operación', operationId);
  return searchBackend(query, { signal });
});

const boundedSearch = pipe(search, timeout(1_500));
const results = await run({}, ['status'], boundedSearch, {
  operationId: 'search-status',
  signal: request.signal,
});
```

La función no instala contexto global ni cambia los argumentos de la llamada externa. En una llamada directa, el primer argumento visible sigue siendo el argumento de negocio; el objeto de ejecución solo se entrega dentro de la función adaptada.

## Transiciones optimistas de `StateMachine`

La opción `{ concurrency: 'reject-stale' }` cambia cómo se confirma una transición decorada. El método captura una revisión al empezar. Cuando termina correctamente, solo cambia el estado si ninguna transición base ocurrió desde entonces. Si otra operación ganó, la promesa rechaza con `StateTransitionConflictError`; `isStateTransitionConflictError` también reconoce errores creados por otra copia del paquete.

```ts
import { StateMachine, TransitionTo, When } from 'annotations-design-patterns';

type DocumentState = 'draft' | 'published' | 'archived';

class Document extends StateMachine<DocumentState> {
  @When('draft')
  @TransitionTo('published', { concurrency: 'reject-stale' })
  async publish(): Promise<void> {
    await persistPublication();
  }
}

const document = new Document('draft');
await document.publish();
```

La política es “primer commit válido”: una transición manual, incluida una transición al mismo estado, invalida el trabajo pendiente. El rechazo no deshace efectos externos del método y no reintenta automáticamente la operación. Conviene que el cuerpo valide o confirme sus efectos de manera compatible con un posible conflicto. Sin la opción optimista, el comportamiento anterior permanece: al terminar, el decorador llama a `transitionTo` de forma virtual.

La confirmación optimista es interna y no llama al override de `transitionTo`. Los cambios manuales mediante un override deben delegar a `super.transitionTo` para actualizar la revisión. No se garantiza detectar cambios ocultos en estado privado de una subclase ni se omiten las guardas al reintentar un conflicto.

## Diagnóstico con handles locales

Las fábricas `circuitBreakerWithHandle`, `keyedLockWithHandle` y `semaphoreWithHandle` devuelven `{ operator, handle }`. Un handle permite consultar copias inmutables de estadísticas; no expone colecciones internas ni crea un registro global. El estado se comparte entre las aplicaciones del operador producido por esa fábrica. Un operador normal mantiene estado por cada método aplicado.

```ts
import {
  circuitBreakerWithHandle,
  keyedLockWithHandle,
  semaphoreWithHandle,
} from 'annotations-design-patterns/operators';

const breaker = circuitBreakerWithHandle({ failures: 5, resetMs: 10_000 });
const lock = keyedLockWithHandle({
  key: ({ args }) => String(args[0]),
  maxQueue: 20,
});
const semaphore = semaphoreWithHandle({ permits: 8, maxQueue: 40 });

const breakerState = breaker.handle.inspect(); // undefined hasta la primera aplicación
const keyState = lock.handle.inspect('customer-17');
const poolState = semaphore.handle.inspect();
breaker.handle.reset();
```

El handle del circuit breaker empieza sin estado observable (`undefined`) hasta que se aplica por primera vez el operador. Después informa `CLOSED`, `OPEN` o `HALF_OPEN`, fallos consecutivos, sonda en curso y hora de apertura. `reset()` limpia el estado y avanza una generación: las operaciones pendientes de la generación anterior, incluidas sondas, ya no pueden cambiar el estado después del reset. No cancela esas operaciones ni revoca permisos; sus resultados de negocio siguen la semántica habitual.

Los handles de keyed lock y semaphore informan `{ active, queued }` por clave. El primero requiere consultar con la misma clave que produce su resolver; el segundo acepta una clave opcional. Los snapshots son inmutables y `inspect` no crea estado para una clave que nunca se usó. Estos son contadores y mecanismos en memoria del proceso actual; no coordinan otros procesos.

## Caché asíncrona externa y CAS experimentales

`asyncCachedFor(ttlMs, options)` es experimental. A diferencia de `cachedFor`, siempre es asíncrono y delega en un `AsyncCacheProvider` que declara explícitamente `capabilities.ttl: true`, e implementa `get` y `set`. Requiere namespace, versión de esquema, una función de clave, codec síncrono, política de fallo del almacén y un límite de I/O finito.

```ts
import { asyncCachedFor, type AsyncCacheProvider } from 'annotations-design-patterns/experimental';

// Contrato ilustrativo del cliente remoto; debe conservar TTL y errores reales.
declare const backend: {
  get(key: string): Promise<string | null>;
  set(key: string, value: string, ttlMs: number): Promise<void>;
};

const provider: AsyncCacheProvider = {
  capabilities: { ttl: true },
  get: async (key) => {
    const raw = await backend.get(key);
    return raw === null ? undefined : JSON.parse(raw);
  },
  set: async (key, value, options) => {
    await backend.set(key, JSON.stringify(value), options!.ttlMs!);
  },
};

const getProfile = asyncCachedFor<unknown, [string], Profile>(60_000, {
  store: provider,
  namespace: 'profiles',
  schemaVersion: '3',
  key: (id) => id,
  codec: {
    encode: (profile) => JSON.stringify(profile),
    decode: (payload) => JSON.parse(String(payload)) as Profile,
  },
  storeFailure: 'bypass',
  ioTimeoutMs: 1_000,
});
```

Usa `storeFailure: 'bypass'` para continuar con el método de negocio cuando falle una operación del proveedor (por ejemplo, un error de permisos o configuración), o `'reject'` para propagar `AsyncCacheError`. Es una decisión explícita: en modo `bypass`, una caché inaccesible puede quedar oculta mientras las llamadas al método de negocio funcionan. Los errores de clave, formato del sobre, esquema y codec siempre rechazan; `bypass` solo cubre operaciones de lectura/escritura del proveedor. `onDiagnostic` recibe los fallos de esas operaciones y sus propios fallos no cambian el resultado del negocio. El operador detiene los pasos posteriores después de una cancelación y no inicia una escritura nueva tras ella. Un I/O ya iniciado puede seguir ejecutándose en el proveedor aunque el consumidor haya cancelado o haya vencido `ioTimeoutMs`: ese límite acota la espera del operador, no el I/O físico. No se implementa deduplicación distribuida de misses ni una garantía general contra escrituras obsoletas; el TTL declarado por el adaptador debe corresponder a una capacidad real.

`VersionedMemoryStore` es una referencia experimental de almacenamiento CAS para una sola instancia. Cada lectura devuelve una versión opaca, presente o ausente; `compareExchange` cambia el valor únicamente si la versión sigue siendo la esperada, y `deleteIfVersion` elimina solo la revisión indicada.

```ts
import { VersionedMemoryStore } from 'annotations-design-patterns/experimental';

const store = new VersionedMemoryStore<string>();
const before = await store.read('job-1');
const result = await store.compareExchange('job-1', before.version, 'claimed', 30_000);

if (!result.exchanged) {
  // Otro escritor modificó la revisión; vuelve a leer y decide según tu dominio.
}
```

El almacén invalida versiones al expirar, escribir o borrar una entrada. Las versiones son opacas y únicas dentro de una instancia. El identificador usa `crypto.randomUUID()` cuando está disponible; el fallback local combina un contador con componentes probabilísticos y no aporta unicidad garantizada entre instancias. Es una referencia local para probar el contrato, no una implementación distribuida. No se deben inferir locks, circuit breakers ni semáforos entre procesos a partir de este ejemplo.

Las versiones de ausencia usan una época global del almacén para evitar retener tombstones por cada clave. Por ello una escritura en otra clave puede invalidar un token de ausencia: hay conflictos conservadores y un CAS puede exigir una nueva lectura aunque esa clave siga ausente. La expiración es perezosa; no hay límite automático de entradas ni barrido en segundo plano en esta referencia.

Los snapshots congelan su estructura, no los objetos guardados. Los valores se conservan y devuelven por referencia: trata esos objetos como inmutables o realiza copias en tu frontera de aplicación. Mutar el objeto original o `entry.value` por fuera del store no avanza la versión y CAS no puede detectar ese cambio. El contrato no promete clonación profunda genérica.

## Observabilidad

Los adaptadores `createCounterSink`, `createSpanEventSink` y `combineEventSinks` son estables. Los callbacks reciben etiquetas acotadas: no se reenvían IDs de operación ni metadatos arbitrarios a las etiquetas del contador. Los errores síncronos y rechazos accidentales de los callbacks se aíslan para que la instrumentación no cambie el resultado del negocio.

Esta protección también cubre un `EventSink` configurado directamente en `run`: su contrato continúa siendo `emit(): void`, sin espera ni backpressure, pero un rechazo asíncrono devuelto accidentalmente queda observado. No convierte el resultado síncrono de negocio en una promesa.

```ts
import { run } from 'annotations-design-patterns/run';
import { createCounterSink, combineEventSinks } from 'annotations-design-patterns/observability';

const counters = createCounterSink((name, labels) => metrics.increment(name, labels));
const events = combineEventSinks(counters, auditSink);
const value = await run(service, ['key'], service.load, {
  operationId: 'load-key',
  eventSink: events,
});
```

`observeOperation` es experimental y se importa desde `annotations-design-patterns/experimental`. Envuelve una capa de operador y reporta un resultado (`success`, `error` o `cancelled`) y duración monotónica por invocación observada. Puede añadir datos de invocación solo con `includeInvocation: true`. Mide cuándo termina el resultado observable de esa capa, no necesariamente cuándo concluye el trabajo físico de un backend compartido. Si `run` rechaza una señal ya abortada antes de entrar en la tubería, esa capa no se ejecuta y no emite observación.

La posición en `pipe` decide qué resultado y cuánto tiempo mide: una capa externa puede incluir los reintentos o ver el fallback como éxito; una interna observa cada ejecución que la alcanza. `cancelled` requiere procedencia de la señal del consumidor; un timeout interno o un error llamado `AbortError` por sí solo es `error`. Los operadores desconocidos se etiquetan como `custom`; los IDs y argumentos opcionales no deben convertirse en etiquetas de métricas. Una promesa nativa sin señal conserva identidad; un thenable genérico se asimila en una promesa. Una subclase hostil de Promise que impida adjuntar observadores puede impedir la medición, conservándose el resultado original.

## Orden de mutaciones en `AsyncMemoryStore`

`AsyncMemoryStore<K, V>` serializa las mutaciones admitidas para una misma clave. `update` ejecuta el updater dentro de esa secuencia, por lo que las actualizaciones concurrentes de una clave no leen y escriben sobre una misma versión anterior. `get` y `has` conservan las lecturas sin espera del último valor confirmado; pueden usarse dentro de un updater y no esperan una mutación pendiente.

```ts
import { AsyncMemoryStore } from 'annotations-design-patterns/store';

const counts = new AsyncMemoryStore<string, number>();
await counts.set('jobs', 0);

const increment = () => counts.update('jobs', (current) => (current ?? 0) + 1);
await Promise.all([increment(), increment(), increment()]);
const total = await counts.get('jobs'); // 3
```

`clear()` y `cleanup()` son barreras de mutación: esperan a las mutaciones por clave admitidas antes que ellas, y las mutaciones nuevas esperan a que la barrera termine. El TTL de una escritura empieza cuando la escritura en cola se confirma. Un updater no debe esperar otra mutación de su misma clave ni llamar y esperar `clear()` o `cleanup()`: esas operaciones esperan al updater y crearían una dependencia circular. No hay detección universal de reentrada. Este orden corrige carreras de 2.2, pero cambia la temporización de esas mutaciones; un updater que antes esperaba una escritura al mismo almacén debe devolver el nuevo valor mediante su resultado.

La cola de mutaciones no aplica backpressure ni limita el número de llamadas pendientes. Un updater lento puede retener las llamadas posteriores y sus argumentos; el consumidor debe controlar esa concurrencia. El TTL no es un temporizador de borrado automático: `cleanup` o el acceso a una entrada expirada hacen la limpieza.

## Elegir el nivel adecuado

Usa operadores locales cuando una sola instancia del proceso basta. Los handles diagnostican su propio estado de fábrica; `AsyncMemoryStore` y `VersionedMemoryStore` implementan contratos locales. El nombre “atomic” o “strong” de una capacidad de un adaptador describe ese adaptador en su ámbito declarado, no una garantía entre máquinas. Para coordinación distribuida hace falta un proveedor probado que defina explícitamente concurrencia, expiración, particiones y fallos de red.
